## 任务

为一条 Hacker News story 生成两张卡片的旁白文案：`event_card` → `atmosphere_card`。

这段文案由 TTS 直接朗读。写的时候想象自己在给朋友讲圈内发生的事：信息密度要够，但口播节奏要对。目标是**句与句之间有纵向推进**——前一句为后一句铺路，后一句在补充或反转前一句，听起来像一段连贯的讲述而不是标题列表。

## 输出

只输出严格 JSON，不要 Markdown 或解释。

```json
{
  "signal": "15-25字，趋势或张力，完整短句",
  "card_narrations": [
    {
      "card_type": "event_card",
      "subtitle_texts": [
        "第一句说清谁做了什么、直接后果或反常识之处，用 20-30 字承载完整因果链。",
        "如果第一句已说清价值，这句可省略。如果需要补充关键机制、代价或对比，用 15-25 字。"
      ]
    },
    {
      "card_type": "atmosphere_card",
      "subtitle_texts": [
        "第一句说评论区在争论什么或补充什么，和 event 部分自然衔接。使用不同的入题方式，不要每次都是"评论区X分成Y派"。用 20-30 字。",
        "最后一句揭示分歧根源或收在一个具体落点上。用 15-25 字。不要添加第三条 subtitle_texts 来补述——如果两句话说不清，宁可把第一句写长一点。"
      ]
    }
  ],
  "scene_elements": [
    {"element_type": "event_card", "props": {"story_index": 0, "source_title": "Original HN title"}},
    {"element_type": "atmosphere_card", "props": {"story_index": 0}}
  ]
}
```

## 句长规则

- 目标 15-30 字，极简事实可短到 12 字，含因果链可长到 35 字。
- 句长必须有变化。用短比说清事实被打散成短句更好：能把因果装进一条中等句就不要拆成两条硬邦邦的短句。
- 过量提示：如果连续出现 3 条以上 15 字以下的短句，听起来像报菜单。

## 衔接规则

- 句与句之间的内容要沿同一语义线向前推，不能跳跃换话题。
- 评论区观点不要写成孤立引述，要串联起来："评论区形成了两种声音——一些人认为 X，但另一批人从 Y 角度提出了不同看法……"
- 不要把因果链拆成两条独立的陈述。把"A 导致 B"写成一条完整句，不要写成"A 发生了。因此 B 发生了。"
- event_card 的最后一句，和 atmosphere_card 的第一句，要有隐性的语义递进，不需要用"此外"或"值得一提的是"等过渡词，但读者应能感受到话题在深化而不是在换台。
- **禁止跨句复述**：相邻 subtitle_texts 之间、event_card 与 atmosphere_card 之间，不得出现连续 12 字以上完全相同的字符串。同一事实如果需要二次提及，必须换措辞、换角度、换位置，不能把前一句原样重写一遍。

## 信息取舍

- 输入里有很多事实时，只保留 2-3 个最能解释冲突的点。
- 删除顺序：宏大评价 → 背景铺垫 → 第二个同质评论 → 形容词和语气词。
- 不要平均用力罗列每个子观点，集中火力讲透主线。

## 输出自检

- **复读检查**：输出 JSON 前，把同一 story 的所有 subtitle_texts 按出现顺序拼成一个长字符串，对比相邻两条；如果任意相邻两条之间存在 12 字以上完全重复的子串，必须重写后句，直到不重复为止。
- **去重后长度**：删掉复读内容后，event_card 的两条 subtitle_texts 合并后应自然落在 30-65 字（2 条），atmosphere_card 落在 30-80 字（2-3 条）；如不足 30 字，说明信息密度不够，需要补充；如超过 80 字，优先压缩最弱的描述而不是叠加新事实。
- **品牌与数字保留**：去重过程中不得删掉故事主体（公司/产品/模型名）和具体数字（金额、百分比、日期）；这些是必保元素，复读检查不能让它们消失。

## 总量控制

- event_card 最多 2 条 subtitle_texts，atmosphere_card 最多 3 条。单条 subtitle_texts 至少 15 字。
- 能在 event 的 2 条里说清冲突全貌的，atmosphere 就只写 2 条。
- 同一 story 内，atmosphere 的 subtitle_texts 总数不得超过 event 的 subtitle_texts 总数 + 1。

## 风格

- 做过功课的人在口播：直接、紧凑、不带套话。
- 语体统一——如果你的 event_card 是书面叙事，atmosphere_card 也不要突然蹦出口语俚语。
- 允许轻微锋芒，但不能阴阳怪气。对圈内术语不做基础科普。
- 每个 story 必须有一个明确落点：钱、权限、稳定性、所有权、开发效率、合规风险、用户体验或生态控制权。没有明显落点就写"谁因此付出什么代价"。
- 不同 story 的表达节奏必须有可感知的变化。atmosphere 的入题方式不能雷同——不可以每次都写"评论区迅速分成两派"或"评论区立刻分成两派"。可以直说争议焦点，可以用一个具体评论做锚点，也可以从事件本身自然引出分歧。
- 禁止在同一 story 内重复使用同一个判断短语或成语（如 "杀鸡儆猴" 出现了第一次就不能出现第二次）。

## 禁止

- 空话：引发关注、备受争议、值得关注、意义重大、持续发酵、成为焦点。
- 不补输入里没有的动机、规模、后果。数字、日期、百分比必须来自输入。
- 不把相近事实改写成更强结论：延迟升高 → 不掉线/断网；绕中继 → 不砍掉 P2P；提案 → 不法律已通过。
- 百分比必须保留原始对象，不能扩大范围。
- 成本判断必须带归因主体："支持者认为成本不高"，不写"几乎没有新增成本"。
- 法律、政策内容必须标来源立场：报道称 / 提案 / 诉讼 / 评论认为。
- 不堆术语。术语只在承载事实或分歧时出现。
- **禁止段落级复读**：LLM 容易把同一段事实写两遍（"X 做了 Y，因此…"紧接着又说一遍"X 做了 Y，…")。自查方式：把同一 story 的所有 subtitle_texts 按顺序拼成一段，相邻两句重叠字数 ≥ 12 即视为复读，必须删掉或换一种说法重写。
- 不给观众下结论。用具体后果表达判断。
- 不反问、不追问、不互动："你怎么看""你支持哪边""你会怎么选"。
- 不截断词和半截短语。枚举用顿号。句号只用于真正句末。
- 不把并列短语拆成病句："他的领域知识。分布式调试能力……" 应写成 "他的领域知识、分布式调试能力……"
- 不把背景状语单独成句："3 月起 API 更新后。" 必须和主句合并。
