## 标题生成规则

【标题目标】
生成类似以下风格的标题（注意：不要使用"社区XX"句式）：
- 《【HN日报】Claude Fable 5 发布：技术突破还是 IPO 造势？》
- 《【HN日报】Claude 被曝"静默降智"：付费用户不能被暗中削弱》
- 《【HN日报】微软 70 个 AI 仓库被投毒：这锅别甩给开源》
- 《【HN日报】Claude 新模型更安全了：开发者却担心它更难用了》
- 《【HN日报】Claude 降智争议升级：安全机制变成商业武器》

【强制要求】
1. 每个标题必须以 **【HN日报】** 开头。
2. 每个标题结构必须是 **【HN日报】事件描述：态度/争议焦点**（冒号后表达态度或争议）。
3. 禁止使用"社区质疑""社区吵翻""社区警觉"等"社区XX"句式。态度直接表达，例如用"付费用户不能被暗中削弱"而不是"社区怒批：付费用户不能被暗中削弱"。
4. 禁止只写事件，不写态度/争议。
5. 禁止只写态度，不写具体事件。
6. 禁止虚构评论中没有出现的立场。
7. 如果评论以质疑为主，态度部分用"质疑""不满""担心""警觉"等词直接表达。
8. 如果评论分歧明显，态度部分用"争议""分歧""两极分化"等词直接表达。
9. 标题要适合 B 站科技区：有冲突、口语化、不标题党、不过度煽动。
10. **标题正文（不含【HN日报】前缀）视觉宽度严格控制在 12-24 个中文字符宽度以内**。计数规则：中文字符、中文标点算 2 宽度，英文字母、数字、英文标点、空格算 1 宽度。生成前必须按此规则算一遍正文宽度，超过 48 宽度（≈24 中文字符）的必须缩短。英文单词较长时（如 Apple Intelligence），优先缩写或换用短词。
11. **必须恰好输出 3 个候选标题**，按点击潜力从高到低排序。少一个都不行。
12. **3 个标题必须有差异化**：1 个技术向（面向开发者），1 个后果向（面向普通用户，强调"影响了谁/会怎样"），1 个争议向（强调立场冲突）。不要 3 个都是技术描述。
13. 3 个标题分别覆盖：信息型、冲突型、问题型。问题型表达“问题卡在哪里”，但不使用问号，不制造悬念党。
14. 避免报告化词汇作为标题核心：未达预期、显著提速、组织架构、产品策略、治理能力。能写成白话因果时，优先写白话。

【推荐标题结构】
A. 《【HN日报】事件描述：争议焦点？》
B. 《【HN日报】事件曝光/发布/翻车：核心矛盾》
C. 《【HN日报】事件引发争议：潜在后果》
D. 《【HN日报】事件升级：不能……》

【品牌与主语规则】
- 如果主事件里有强品牌、平台或责任主体，必须把它放到标题开头，例如 `NVIDIA`、`Anthropic`、`微软`、`Steam`。不要把泛机制词抢主语。
- 标题结构优先是"品牌/平台 + 做法/变化 + 后果"，例如 `Meta 用 AI 客服，账号被盗`。
- 安全事故标题：受害者/平台 + 出事动词 + 数字/具体后果。动词必须准确：`账号被盗`、`账号被接管` 优于 `账号交出去`。

【冲突词清单】
- 事实明确时可用：掉线、涨价、封禁、停服、被盗、被接管、失守、被滥用、关闭、砍掉。
- 事实不明确时降级：延迟升高、绕路、被质疑、引发争议、用户反馈。
- 禁止：震惊、炸裂、重磅、全网、彻底改变、时代变了、封神、翻车了、永久游玩权、永久拥有。

【动词准确性】
- 安全事故：被盗 / 被劫 / 被接管 / 失守 / 被滥用，禁止"交出账号 / 放走账号 / 送走账号"。
- 归因有争议时用"被质疑 / 引争议 / 绕路 / 延迟飙升 / 用户反馈"，不要替争议下结论。

【其他限制】
- 不编造数字、年份、公司动作、法律结果、用户规模；所有具体数字必须来自输入。
- 不用 emoji、感叹号、问号、方括号装饰、营销口号。
- 中文优先，必要英文产品名保留；中英文混排紧凑。
- 主推标题只押一个主冲突，不要两个 story 硬拼。
- 3 个候选角度要不同：后果型、机制型、反常识型等。

## title

- 每个标题正文（不含【HN日报】前缀）视觉宽度 12-24 中文字符宽度。计数：中文字符/中文标点=2，英文字母/数字/英文标点/空格=1。生成后按此规则算一遍正文宽度，超过 48 的必须缩短。英文单词较长时优先缩写或换用短词。
- 每个标题必须以 **【HN日报】** 开头，结构为 **【HN日报】事件：态度/争议**。
- 禁止使用"社区质疑""社区吵翻""社区警觉"等"社区XX"句式。
- 主推标题必须能回答"点开后我会看到什么冲突"。如果只是"X 与 Y 发生了"，要改成"X 做了什么，导致/结果谁付出什么代价"。
- 主推标题优先使用观众能复述的白话冲突，例如“裁员没让 Meta AI 变快”，不要只写“重组未达预期”。
- 标题里如果出现两个互不相关的公司/产品/事件名，重写成单一主事件。
- 不要使用"今日速览""AI资讯""科技早报""HN每日观察"作为标题主体。

## description

- 一个自然段，简洁明了。**必须分句概括当日全部故事**。它会出现在发布简介里，不要写成媒体通稿或法律公告。
- **第 1 句**：展开标题承诺的主事件，给出机制、数字、后果；优先用白话，不要写成报告摘要。
- **中间句**：为 other_stories_json 中的**每一个故事**各写一句概括（核心事件 + 关键数字 + 品牌名），用中文句号分隔。即使是与焦点故事同一品牌（如焦点是苹果涨价，other 里有苹果 M7），也必须各写一句。
- **最后一句**：收束当日共性话题。
- 每句不超过 36 个汉字；超过就删弱背景，不要用逗号继续堆事实。
- `description` 默认写成 4-5 个短句：主事件 1-2 句，其他 story 各 1 句，共性收束 1 句。不要把多个 story 合成一句。
- 绝对禁止分号，包括 ASCII `;` 和中文 `；`；每句最多 2 个逗号。
- 如果 description 中任何一句超过 36 个汉字，必须改写为两句短句，而不是继续压缩成长句。
- 不使用“彻底、永久、必然、全面、封死”等终局化词汇，除非输入明确写出没有例外、已经生效、且不可逆。
- 数字产权、平台下架、应用商店控制类简介，优先写“下架、移除、限制分发、渠道收窄、长期可访问变差”，不要写“彻底消失、封禁应用、永久失去”。
- **自检清单**（生成 JSON 前逐项核对，缺少任何一项则视为不合格，会被整段丢弃重试）：
  - ① description 是否提到了焦点故事的品牌？___（必须填 是）
  - ② description 是否逐一提到了 other_stories_json 中每个故事的品牌/产品？___（必须填 是，列出每个品牌名）
  - ③ description 是否包含了每个故事的关键数字？___（必须填 是）
  - 如果任何一项是"否"，重写 description 直到全部满足。
- 使用 `article_summary` 和 `key_points` 中的具体细节。不要复读标题；不要写"本期视频将带你了解""你怎么看"等套话。

## cover_title / cover_tags / cover_highlights

- `cover_title` 是封面缩略图上最大的大字，必须比 `title` 更短。默认使用 `\n` 分成两行：第一行写强主体/事件对象，第二行写核心判断/后果。只有总宽度不超过 16、且单行不超过 8 个中文字符宽度时，才允许单行。
- **强主体优先**：如果主事件涉及强品牌、平台、公司或责任主体，`cover_title` 必须把它放在开头或第一视觉位置；不要为了抽象机制把品牌删掉、挪到 `cover_tags`，或只写"裁员不等于提速"这类失去主体的判断。示例：`Meta AI重组未达预期` 优于 `裁员不等于提速`。
- **白话但克制**：封面大字优先使用“没变快 / 引发质疑 / 风险暴露 / 成本抬升 / 遭遇瓶颈”等一眼能懂的判断；少用“未达预期 / 显著提速 / 产品策略”等报告化词。禁止"难绷 / 崩了 / 完蛋 / 打脸 / 真香 / 上车 / 豪赌 / 算账 / 送钱 / 承认无效"等口语化、情绪化、调侃式或过度定性的词。
- **默认手动两行**：在自然语义边界插入 `\n`。两行都必须是完整语义块，不要让单个字、半个词或孤立后缀单独成行。示例：`Meta AI重组\n未达预期`、`日本裁定AI\n非发明人`、`Claude Code\n隐写争议`；禁止 `Meta AI重组未达预\n期`。
- **事件 + 态度融合**：用"谁 + 做了什么/发生什么 + 社区怎么看/争议在哪"的结构，既说清事件又点到社区态度。不要只写纯事实罗列，也不要只写态度而丢了具体事件。例如：
  - ❌ "OpenAI发布自研芯片Jalapeño"（纯事实，没态度）
  - ❌ "社区质疑技术细节不足"（纯态度，丢掉了事件主体）
  - ❌ "AUR 408包被植入内核级Rootkit"（术语太多，路人看不懂）
  - ✅ "408个开源软件包被植入恶意程序"（事实 + 恶意定性）
  - ✅ "OpenAI自研芯片水分引质疑"（事实 + 社区态度）
  - ✅ "Anthropic蒸馏指控现双标争议"（事件 + 态度）
  - ✅ "开源仓库遭大规模投毒"（事实 + 恶意定性）
- 态度来源必须是评论分析中真实存在的立场（质疑/争议/不满/支持等），不能凭空添加。
- 如果主推标题里有数字后果或态度关键词，`cover_title` 必须保留；如果空间不够，优先保留"强主体 + 核心后果/判断"，把次要机制放到 `cover_subtitle`。
- `cover_tags` 输出 1-2 个短标签，每个 4-10 个中文字符；用于补充主事件的角度，不重复 `cover_title` 的主信息。
- `cover_highlights` 是 `cover_title` 中需要橙色高亮的关键词数组（必须输出 1-2 个词，不能为空）。这些词会在封面上显示为醒目的橙色，用于在缩略图中抓住观众眼球。从 `cover_title` 中提取最吸引眼球的部分。选择优先级：品牌/产品名 > 数字后果 > 冲突动词。示例：
  - "AUR 408包被植入内核级Rootkit" → ["Rootkit"]
  - "Fedora AI Agent投毒发行版中招" → ["投毒"]
  - "德国裁定Google AI摘要担责" → ["Google", "担责"]
  - "Anthropic发布Claude 4.7" → ["Anthropic", "4.7"]

## cover_subtitle

- 三行，每行以 `— ` 开头。
- 每行 6-12 个中文字符或等长中英混排短语。只写短语，不写完整句，不加句号。
- 三行都服务封面主事件：第一行写具体对象，第二行写冲突/代价，第三行写机制/受影响人群。

## tags

- 5-8 个中文标签。主题优先，具体公司/产品不超过 3 个。
- 每个当日故事至少对应 1-2 个标签（从该故事的核心主题/技术/行业提取），不能只覆盖焦点故事。
- 适合 B 站科技区检索，例如：`AI`、`开发者工具`、`开源`、`游戏产业`、`网络协议`。

## 失败保护

- 如果输入不足以生成安全文案，输出空 `title / description / tags`。
- 如果无法判断某个高冲突词是否被事实支持，降级为中性词：`影响`、`绕路`、`延迟升高`、`被迫改用`、`引发争议`、`用户反馈`。
- 数字产权标题不要写“永久游玩权”“永久拥有”；优先写“长期访问权”“购买权变弱”“实体盘退场”“数字购买争议”。
